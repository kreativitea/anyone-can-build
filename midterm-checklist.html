Midterm practical — what I check

At a glance

  • Starts: Friday Oct 30. The repository, Gaidai Eats, opens that day.
  • Due: 6 PM, Thursday Nov 5 (Japan time).
  • Time: at least two hours. Start early: a review that finds a problem sends you back.
  • Where: your own private copy of Gaidai Eats. Its README says how to make it.
  • What I grade: what is on main in your repository at 6 PM on Nov 5.

What you do

  1. Make your copy of Gaidai Eats, as its README says.
  2. Take the three plans in docs/plans/ through the loop. Someone else wrote them. Most have mistakes in them; one may have none. Building a plan as it is builds its mistakes too, so fix each plan before you build it. If a plan has no mistake, say so, with your reasons: that is a correct review.
  3. Build five of the ten features in FEATURES.md. Write your own plan for each one, from docs/plans/TEMPLATE.md, and take it through the loop the same way.
  4. Write three lines in your tracker for each plan (see the end of this page).

The loop is the one from class: Plan · Review the plan · Build · Review the result · Check it live. The checklist below is what I look for at each step, for every plan: the three given plans and your five.

The loop, step by step

1. Plan

  • Section 1 is the idea loop: the problem, what it costs, the change, what gets better, and whether you checked it with a real person. Write it about the person using the app, not about the code. I grade this section on its own.

2. Review the plan

  • You read the plan yourself, next to DESIGN.md and AGENTS.md.
  • An agent reviewed it in a new session, using docs/reviewer.md.
  • Every objection is in section 5, yours and the agent's. Each one says accept or reject, and why, in your own words. "The agent approved it" is not a decision.
  • Every objection you accepted changed the plan. I check that the change is there.
  • Section 3, done when, can be checked by a machine. Each line reads when ___, it should ___. There is at least one edge case, and the expected test count is right.
  • You committed the reviewed plan before any code for it. I check the order in the commit history.

3. Build

  • Each plan has its own branch and its own worktree: make worktree BRANCH=<name>.
  • Nothing is committed straight to main. Every change reaches main through a pull request.
  • There are new tests for the new behaviour, one for each done when line.
  • make check passes, and the test count is the one your plan expected. If it is not, the plan says why.

4. Review the result

  • An agent reviewed the change in a new session, from the diff, using docs/reviewer.md.
  • Every objection is decided: accept or reject, and why. Write them in the pull request, or add them to the plan.

5. Check it live

  • The pull request is merged in your own repository.
  • Its description has at least one sentence in your own words, saying what the change does. An empty description earns nothing for this line.
  • You merged one pull request at a time. After each one, you pulled main, make check passed again, and you removed the worktree (git worktree list shows only your main folder).
  • You ran it (make run), and it does what your done when says.

Your prompts

  • Every prompt is committed in docs/prompts/, in the same pull request as the change it asked for. Never change them after they are written. I read them: they show which decisions you made, and which you gave to the agent.

The two for an A:

  • Your own improvement. Find something the site does badly that this repository does not talk about. Change a plan or DESIGN.md for it, and take that change through the loop.
  • Parallel agents. Build two or more pieces of work at the same time, each with its own agent in its own worktree. Choose them so they touch different parts of the app (FEATURES.md says which part each feature touches), and merge them without collisions.

More than five features does not raise your grade by itself.

Below the C: each feature that works is 15 points. If any of them did not go through the loop, the total stops at 69.

Extra credit: an eval (5 points)

The site's code is deterministic: the same input always gives the same output. But in a few places, whether the answer is right depends on what the person meant. No single test can settle that. It can only be scored over many cases, the way you scored your classifier.

Find one of those places and write an eval for it, in docs/eval.md:

  • a set of cases, written before you change anything
  • for each case, the answer a person would expect
  • the score before your change, and after it
  • why this place needs an eval, and not only unit tests

Points above 100 count.

Last: your tracker

  • For each plan, three lines: what the change does · one decision that was yours, not the agent's: a mistake you found, an objection you rejected, or why a plan needed no change · one thing the agent did that you did not expect.

What earns no points, even when every file is there

None of these fails the course. Each one means the step it belongs to earns no points:

  • a plan built as it was given, with no review
  • a review where the agent decided for you
  • code committed before the reviewed plan
  • a pull request with no words of yours
  • a commit straight to main

About your agent

You may give this page to your agent. An agent works best when it knows what done means. But an agent can write every file on this list, and you would still earn no points for the steps that need your decisions. What I check is the part only you can do: the decisions, and whether they are yours. Some mistakes in the plans are about the code, and an agent will find them. Some are about what the app is for, and an agent will not find them unless you tell it.

Keep every name and every example row made up. Never put a real person's data in a plan, a prompt or a post.
