Midterm practical — what I check

Oct 30, remote. The repository opens on Oct 30, when the midterm starts. Due 6 PM, Thursday Nov 5 (Japan time): what is on main in your repository at that time is what I grade. Plan for at least two hours of work, and start early in the week: a review that finds a real problem sends you back, and that takes time. You get Gaidai Eats, a small review site you have not worked in, in your own private repository, and the plans in its docs/plans/, written by someone else. Most of them have mistakes in them; one may have none, and saying so, with your reasons, is a correct review. You take each plan round the agentic engineering loop, on your own: Plan · Review the plan · Build · Review the result · Check it live. Your repository is what I grade. This page is everything I look at, in the order I look at it.

You may give this page to your agent. That is allowed, and it is part of the skill: an agent works best when it knows what done means. But an agent can write every file on this list and still fail it. What I am checking is the part only you can do: the decisions, and whether they are yours. Some of the mistakes are about the code, and an agent will find them. Some are about what the app is for, and an agent will not, unless you tell it.

For each plan, the ones you are given and the ones you write for the features (below):

1. Plan

The given plans are written for you. Building one as it stands builds its mistakes too. Your job is to make it right, at step 2, in the plan's own sections. A plan you write yourself, for a feature, starts from docs/plans/TEMPLATE.md.

  • [ ] Section 1 goes round the idea loop: the problem, what it costs, the change, what gets better, and whether you checked it with a real person. It is about the person using the app, not about the code. I grade it on its own.

2. Review the plan

  • [ ] You read it yourself, beside DESIGN.md and AGENTS.md, and had it reviewed in a new session, with docs/reviewer.md.
  • [ ] Every objection is in section 5 of the plan, yours and the agent's, with accept or reject, and why, in your own words. "The agent approved it" is not a decision.
  • [ ] If you accepted an objection, the plan changed. I check that the change is there.
  • [ ] After your review, the plan is right: section 3, done when, is sentences a machine can settle, when ___, it should ___, with one edge case, and the expected test count is correct.
  • [ ] The reviewed plan is committed before any code for it. I read the commit history to check the order.

3. Build

  • [ ] On its own branch, in its own worktree (make worktree BRANCH=<feature>), one per plan. Nothing is committed straight to main. Every change reaches main through a merged pull request.
  • [ ] New tests for the new behaviour, matching your done when sentences.
  • [ ] make check passes, and the test count is the one your plan expected. If it is not, the plan says why.

4. Review the result

  • [ ] Reviewed in a new session, from the diff, with docs/reviewer.md.
  • [ ] Every objection decided: accept or reject, and why. Written in the pull request, or added to the plan.

5. Check it live

  • [ ] The pull request is merged in your own repository. Its description is at least one sentence in your own words: what this change does. An empty description fails this line.
  • [ ] Merged one at a time. After each merge, main is pulled, make check passes again, and the worktree is removed (git worktree list shows only your main folder).
  • [ ] You ran it (make run), and it does what your done when says.

Your prompts

  • [ ] Every prompt is committed, in docs/prompts/, in the same pull request as the change it asked for. Nothing in them changed after it was written. I read them: they show which decisions you made, and which you asked the agent to make.

The features

FEATURES.md lists ten features. Build five of them, the same way, each with its own plan, round the loop.

  • [ ] Five features complete. Complete means every box above is ticked for it: its own plan, reviewed and committed before the code, built on its own branch, reviewed, merged.
  • [ ] Which features, and why. In docs/why-these-features.md: which ones you chose, in what order, and why those, for the people this site is for. Say what you left out and why.

How it becomes a grade.

  • C · Guided (79). You did the assigned work, following the process, with nothing skipped: every box above ticked, by you, for the given plans and five features.
  • B · Independent (89). Given a goal, you chose the steps yourself and can explain them: C, and docs/why-these-features.md, which features you chose and why, for the people this site is for.
  • A · Initiative (95, or 100 for both). B, and one or both of these: your own improvement, something the site does badly that this repository does not talk about, a plan or DESIGN.md changed for it, and taken round the loop; and parallel agents, two or more pieces of work built at once, each in its own worktree, split so they touch different parts of the app (see FEATURES.md), and merged without colliding.

More features than five do not raise the grade by themselves. Below the C, every feature that works counts 15 points; if any of them did not go round the loop, the total stops at 69.

Extra credit (5 points): an eval. The site's code is deterministic: the same input always gives the same output. But a few places in the site need test cases that look more like testing an AI than testing a function: whether the answer is right depends on what the person meant, so no single test can settle it, and it can only be scored over many cases. Find one, and write an eval for it: a set of cases written before you change anything, the answer a person would expect for each, and the score before and after your change. Say why that place needs an eval and not only unit tests. Put it in docs/eval.md.

Last: in your tracker

  • [ ] For each plan, three lines: what the change does · one mistake in the plan that you found, not the agent, and what you decided · one thing the agent did that you did not expect.

Keep every name and every example row made up. Never a real person's data, in a plan, a prompt or a post.

What fails, even when every file is there: a plan built as it was given · a review the agent decided for you · code committed before the reviewed plan · a pull request with no words of yours · commits straight to main.
