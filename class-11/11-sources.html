Class 11 — Sources

Not homework. These are the sources behind Class 11's claims, so that any of them can be checked. Most of the class is the course's own material: Timeline, the to-do app and the split-bill project with its yen bug were made for the course. The four-band pyramid and AI's test pyramid are the instructor's own. What comes from outside is where the field's words and rules come from: Dijkstra's line on testing, the testing pyramid, Google's test sizes, test doubles, flaky tests, test-driven development, maker-checker, and one AI model's habit of making tests pass the wrong way.

Test Hygiene

  • Edsger W. Dijkstra, in J. N. Buxton and B. Randell (eds.), Software Engineering Techniques (NATO Science Committee, report of the conference in Rome, 27–31 October 1969, published April 1970), p. 16: "Testing shows the presence, not the absence of bugs." This is the line behind Presence, not absence. The slide says it in its own words and marks it as paraphrased.
  • Edsger W. Dijkstra, Notes on Structured Programming (EWD 249, August 1969; second edition April 1970), in the section On the reliability of mechanisms. It has the longer form: testing can show bugs "but never to show their absence!" This is the sentence said aloud on Presence, not absence. The same sentence is also printed on p. 66 of the 1969 NATO report above. Readable without programming.
  • Coverage.py, documentation: a coverage tool works by "noting which parts of the code have been executed". It records what ran, not what was checked. This is the definition on The number that flatters you.
  • Richard A. DeMillo, Richard J. Lipton and Frederick G. Sayward, Hints on Test Data Selection: Help for the Practicing Programmer (IEEE Computer, April 1978) is the paper usually named as the start of mutation testing, behind Mutation testing. IEEE's page refused the fetcher. It opens in a browser, and the full text needs a library subscription.
  • Mike Cohn, The Forgotten Layer of the Test Automation Pyramid (Mountain Goat Software) is the origin of the testing pyramid on The shape. In his version, unit tests make the base, user-interface tests are at the top, and there are as few of those as possible. His middle layer is called service. The course uses the more common names integration and end-to-end. He also describes it in his book Succeeding with Agile (2009).
  • Martin Fowler, Test Pyramid gives the history: Cohn "originally drew it in conversation with Lisa Crispin in 2003-4". Read it for the history, not as the origin.
  • James Whittaker, How Google Tests Software, Part Five (Google Testing Blog, 23 March 2011): Google's small, medium and large tests, "emphasizing scope over form". A medium test covers two or more features. A large test covers real user scenarios. These are on Test sizes at Google. The same text became chapter 1 of the book by Whittaker, Jason Arbon and Jeff Carollo, How Google Tests Software (Addison-Wesley, 2012). The book is not free.
  • Bazel, Test encyclopedia: Bazel is Google's build tool, released as open source. It adds the size enormous, whose default time limit is 3,600 seconds, an hour. This is the top band on Test sizes at Google.
  • Gerard Meszaros, Test Double, Fake Object and Mock Object are the draft chapters of his book xUnit Test Patterns (2007), where the three terms on Test doubles come from. Needs programming to read.
  • Martin Fowler, Mocks Aren't Stubs (revised 2 January 2007) is the essay that made Meszaros's words widely known: a test double is "the generic term for any kind of pretend object". Needs programming to read.
  • The stand-ins on There is always a mock: freezegun, fakeredis, moto and Python's own unittest.mock.
  • John Micco, Flaky Tests at Google and How We Mitigate Them (Google Testing Blog, 27 May 2016): a flaky result is "both a passing and a failing result with the same code". This is the definition on Flaky test.

Agentic Testing

  • Anthropic, Claude 3.7 Sonnet System Card (24 February 2025), section 6, Excessive Focus on Passing Tests, p. 22. The model sometimes passed tests by "directly returning expected test values rather than implementing general solutions", which is number 4 on Four ways a test goes green, and the code stays wrong. The same section also reports the model changing tests "to match the code's output", which is number 1. The example on the slide is made up, on the class's own yen bug.
  • Basel Committee on Banking Supervision, Framework for Internal Control Systems in Banking Organisations (September 1998), Principle 6, segregation of duties: one person should not hold both the "approval of the disbursement of funds and the actual disbursement". This is the banking rule behind maker-checker on Adversarial review. The document does not use the name maker-checker, and who first used that name could not be established.
  • Kent Beck, Canon TDD (11 December 2023) is his own short description of test-driven development, on Test-driven development. He calls it "my rediscovery of TDD": he made it widely known with his book Test Driven Development: By Example (Addison-Wesley, 2003), but he does not claim to have invented it.
  • Claude Code, Commands: /security-review, the command mentioned on An AI security review. It "Reviews the diff between your branch and origin's default branch", so it checks a change, not the whole project.
  • Martin Fowler, Continuous Integration describes the practice named on Where the checks run, and its history. Needs programming to read.
