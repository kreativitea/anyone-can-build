Class 10 — Additional content

Assigned after class: do it before next Friday. It takes about two hours. This is the week's main homework: you take a small real app apart with your agent, and add two features to it.

Do: add likes and follows to Timeline

Timeline is the Twitter-like app from Friday. Its code is small on purpose, and it is written in the three parts you learned.

The repository: <https://github.com/kreativitea/anyone-can-build-timeline>

  1. Make your own copy, start from Friday's version, and run it. Open the repository on GitHub and press Fork to make your own copy. Then clone your fork: git clone https://github.com/YOUR-NAME/anyone-can-build-timeline.git, with your GitHub name in place of YOUR-NAME, and cd anyone-can-build-timeline. The repository has changed since Friday: it already has likes and many other features. So start a branch from the version we used in class, before any of them, and do all your work on it: git switch -c homework 997a6453. 997a6453 is the start of that commit's name; your branch is called homework. Run git log --oneline -1 to check: it should say Log each new post. In the folder, run make test: every check should pass. Then run make run and open http://localhost:8009 in two windows, one of them private. Post from each.
  2. Ask your agent to explain the architecture. Open your agent in the folder (it reads AGENTS.md first) and ask: explain this app's architecture. Which file is the frontend, and what is inside it? Which part of server.py is the controller, the model and the view? Where does the data live? Then write the answer in your tracker, in your own words, in five lines or fewer. If you cannot say it yourself, ask the agent again until you can.
  3. Add likes, then follows, each with a test. Likes first: a person can like a post and see how many likes it has, and nobody can like a post twice. Then follows: a person can follow someone and see a timeline of the people they follow. Decide one thing first: Timeline does not know who you are. It has no accounts, and the name typed in the box is all it has, but a like has to know who liked it and a follow has to know who follows. Decide with your agent how Timeline will know (the name in the box is enough), before you add either feature. Then, before your agent writes any code, tell it which parts and which tables you expect to change, and ask it whether you are right. Build each feature together. Add a test for each rule, nobody likes a post twice and you see the posts of the people you follow. A test is a small program that checks one rule, like the one that broke in class when the limit changed; next Friday is all about them. Your agent writes the two tests, and your job is to read each one and say which rule it checks. Run make test until both pass. Both features change the data, so both change all three parts: you modelled them on Friday, and now you build them.
  4. Write three lines in your tracker. Which parts changed, why each one had to, and one thing the agent did that you would not have expected.
  5. Commit, and push your branch to your fork: git push -u origin homework. Put the link to your branch in your tracker: your fork's page on GitHub, with homework chosen in the branch menu.

Keep your data made up. Every name and post in Timeline is invented. Never put a real person's name or messages into it, or into your agent.

Read

  • MDN Web Docs, MVC (~3 min: read down to MVC on the web; free, no account). The reference most web developers use, on the inside of the backend, which you opened on Friday. Its model "Manages data and business logic": it holds the business logic, and it is the part that reads and writes the database. Then find the three parts in Timeline's server.py.
  • Jesse Chen (Meta), Threads: The inside story of Meta's newest social app (2023; ~2 min: the section Planning and developing Threads; free). One of the engineers who built Threads says that "Instagram uses Python (Django) for its backend", and that Threads reused Instagram's backend: its "data models, business logic, security features". New apps went in front of a backend that already existed, which is the case study from Friday. Leverage means make use of, and a tech stack is the set of tools a product is built with.
  • Kirsten Westeinde (Shopify), Deconstructing the Monolith (2019; ~4 min: the sections Monolithic Architecture, Advantages of Monolithic Systems and Disadvantages of Monolithic Systems; free). An engineer at Shopify, which runs online shops, on what happened when every part of their code could reach every other part: it "required a lot of context to make seemingly simple changes". It is the test from Friday, when something changes, how much else has to change?, failed at a real company. A monolith is one big program holding every part. Coupling means how much one part depends on another; a later class is about it. Stop at Microservice Architecture.
  • Android Developers, Guide to app architecture (~5 min: read the first section; free). How Google tells people to build a phone app: a screen, and a ViewModel behind it, which is the shape from Friday's phone slide. You do not need to understand the code on the page.
  • Kateryna Semenova (Android Developers), Performance and Velocity: How Duolingo Adopted MVVM on Android (2021; ~4 min: the sections Introduction and The Android Reboot; free). The Duolingo app grew slow and broke more often as features were added, and its team rebuilt it with a ViewModel behind each screen, so they could "clearly document what logic should go into what files". The phone slide from Friday, in an app you may have used. The post was written by Google to show off a good example, so it only tells the success. Skip the names of tools (Dagger, Hilt); App not Responding errors are when an app freezes.
  • MDN Web Docs, What is JavaScript? (~3 min: the section A high-level definition; free, no account). One button built in three steps: HTML gives it its structure, CSS its looks, and JavaScript its behaviour, the inside of the frontend from Friday. "The three layers build on top of one another nicely." You can bet means you can be sure. Stop at So what can it really do?
