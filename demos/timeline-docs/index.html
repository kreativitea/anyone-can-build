Documentation across the SDLC

The documents of the SDLC, each one written for Timeline

In a large company, each stage of the SDLC has its own documents. Different people write them, and each one is reviewed before the work moves to the next stage. Below are twenty-one of them, in order, each one written for Timeline, the small Twitter-like app from Classes 9 to 12.

This is the most rigorous version: a project at a big tech company. Smaller companies skip some of these steps or put two documents into one. Each document says what a small team usually does instead.

Every person, quote and data row on this page is made up, and so are the dates and numbers in the written examples. A green line at the top of a document means it is the real one, from the Timeline repository. An orange line means Timeline does not have this document, and it is written here as a team would write it. Figma, Linear, Jira and GitHub are named only as examples of such tools.

Press release

Timeline: one page where everyone in the room sees every post

Osaka, 11 May 2026. Today we launch Timeline, a page where a class, a club or a team posts short messages and everyone sees them, newest first. There is no account to make and nothing to install: open the page, type a name, and post.

Group chats bury announcements under conversation, and most class tools ask for a sign-up first. With Timeline, a post appears on every open screen within a second.

"I put the room change on Timeline and the whole club saw it before I sat down," said a club leader who tried it.

Open timeline.example on any phone or laptop to start.

FAQ

For users

Do I need an account? No. You type a name. It is shown on your posts.

How long can a post be? 280 characters.

Can I add a picture? Not in the first version.

For the team

Why no accounts? Every account is a sign-up page people leave at. We would rather lose some control than lose the first post.

How do we know it worked? If people who arrive post during their first visit. The PRD gives the number.

Problem

People in one place (a class, a club) need to see each other's short messages at once. Group chats bury them, and most tools ask for an account first.

For whom

Students in a room or a club, on a phone or a laptop. Many read English as a second language.

Requirements

#Requirement
R1Type a name and post. No account.
R2A post is 1 to 280 characters after spaces are trimmed; a name is 1 to 40.
R3Every open window shows a new post within one second, newest first.
R4If the server cannot be reached, the page says so, and recovers by itself.
R5Large type and high contrast, readable from across a room.

Accounts, follows, replies, pictures.

GoalPeople who arrive take part, not only read.
Success metricFirst-visit post rate: of the people who open Timeline for the first time, the share who send at least one post during that first visit.
Target and time40%, measured over the four weeks after launch (11 May to 7 June 2026).
Guardrail metric7-day return rate stays at or above 25%: of first-time visitors, the share who open Timeline again within 7 days. If we raise posting by making the first visit annoying, this number falls.

The product spec

1. The problem

When two people use the same app, each needs to see what the other posted. A page that keeps everything in the browser cannot do that: each person's device keeps its own copy. Timeline is a small Twitter-like app built to show the difference. One version keeps everything in the page, and the other has a backend that every window shares.

2. Not in this version

  • No accounts, passwords or sign-in. Each window types a display name.
  • No realtime connection (no WebSockets). The page asks for new posts once a second.
  • Nothing reachable from another machine. The server listens on 127.0.0.1 only.
  • No libraries, no install, no build step.

The engineering design

4. The three parts

the browser                          the server                   the store
index.html · style.css · app.js  ──  server.py  ──────────────────  timeline.db

The model's rules: text is not empty after trimming · text is at most 280 characters · author is not empty, at most 40 characters. The server checks them even though the page checks for an empty post too, because a user can change anything that runs on their own device.

5. The data model

usersposts
idinteger, primary key, given by SQLiteidinteger, primary key, given by SQLite
nametext, the display name, uniqueauthor_idinteger, foreign key: the id of a row in users

6. How I will know it works

  1. When a post is sent with text, it should come back with an id and a time, and the same name should always point at the same user.
  2. When a window asks for posts after an id, it should get only newer posts, oldest first.
  3. When two windows are open on the backend version, a post from one should appear in the other within a second.
  4. And when it goes wrong: when a post is empty, or longer than 280 characters, the server should refuse it and say which rule it broke. When the server is stopped, the page should say Cannot reach the server, and recover by itself when the server starts again.

ADR 0002: The page asks for new posts once a second (polling)

Date
2026-04-20
Status
Accepted
Decided by
Ravi (tech lead), Tomás
Context

Requirement R3 in the PRD: every open window shows a new post within one second. The server uses only the Python standard library.

Options
  1. Polling. Every second, each window sends GET /posts?after=<last id>.
  2. WebSockets. The server keeps a connection open to each window and sends each new post at once. The standard library has no WebSocket server.
Decision

Polling. It is the simplest thing that works, and it needs no library.

What it costs
  • A post can take up to one second to appear.
  • Each open window sends one request a second, even when nothing is new. 200 open windows is 200 requests a second.
When to look at this again

If the server spends more time answering "anything new?" than saving posts, or a post must appear faster than a second.

Notes for the privacy review

  • A name, and the words people type, can identify a living person. We treat both as personal information under APPI.
  • The page tells people why we keep each item (APPI asks a business to state its purpose of use). One line under the post box links to this note.
  • The visitor id does not name anyone by itself. APPI has a separate group for data like this, personally referable information, with rules for passing it to a company that could connect it to a person.
  • The analytics tool is run by a company outside Japan. The privacy reviewer decides whether that needs the user's consent under APPI's rules on sending data abroad. Until then, events carry no names and no post text.
  • No post text, names or logs go into an AI tool.
  • Open question: does the log need the post text at all, or only the time and the post's id?

TL-58 · A new post says "9 h ago"

Found
2026-05-28, QA run, step 3
Severity
S2, major. Every new post shows the wrong age for every reader in Japan. Nothing is lost.
Owner
Tomás
Steps
  1. On a computer set to Japan time, run the server and open Timeline.
  2. Post anything.
  3. Read the time under the post.
Expected

just now

Actual

9 h ago

Cause

The server saves created_at in UTC, as the plan says, but writes it as 2026-05-28 01:05:00, with nothing that says it is UTC. Chrome reads a date written that way as local time. So 01:05 UTC (10:05 in Japan) is read as 01:05 in Japan: nine hours ago. The tests checked that created_at exists, not what it says.

Fix

PR #22: write ISO 8601 with the offset, 2026-05-28T01:05:00+00:00, which every browser reads as UTC.

Test

test_created_at_says_it_is_utc checks that created_at ends in +00:00. Count 16 → 17.

What happened

Metrics this plan serves (from the PRD)

  • First-visit post rate = first-time visitors with a post_sent in their first visit ÷ first-time visitors with a page_opened. Target 40%.
  • 7-day return rate (guardrail) = first-time visitors with another page_opened within 7 days ÷ first-time visitors. At or above 25%.

A visit ends after 30 minutes with no event. First-time means the browser had no visitor_id yet.

EXP-1 · A line under the name field

Owner
Lena (data scientist)
Status
Finished
Why

Four weeks after launch, the first-visit post rate was 31%, under the PRD's target of 40%. In the UX test, 3 of 5 people stopped at Your name. P2: "Is this my real name?"

Hypothesis

If a line under the name field says Any name. It is shown on your posts., more first-time visitors will post.

Version A (control)The page as it is today
Version BThe same page, with that line under the name field
WhoFirst-time visitors only, half to each version, by visitor_id, so one person always sees the same version
MetricFirst-visit post rate
Guardrail7-day return rate. Stop the test if B is more than 2 points lower.
Size and lengthTo see a change from 31% to 36%, we need about 1,400 first-time visitors in each version. At about 200 a day, that is 14 days (22 June to 5 July 2026): two full weeks, so weekdays and weekends both count.
What we do with each result
  • B is higher and the guardrail holds: ship B to everyone.
  • No clear difference: keep A, and go back to research on why people do not post.
  • B is lower, or the guardrail drops: remove B.

We do not look at the result before day 14, and we do not stop early because B looks good.
